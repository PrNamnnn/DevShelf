## What it is

State is data a component remembers between renders. `useState` returns the current value and a setter. Setting state asks React to render again with a new value.

## Why it exists

A local variable resets on every call and changing it doesn't update the screen. State survives renders and triggers them.

## How it works

Every screen update has three steps: **trigger, render, commit**. Rendering is React calling your components. Committing is React applying the minimal DOM changes, after which the browser paints.

A state value is fixed within a render. It's a snapshot.

React waits until all the code in an event handler has run before processing updates, which is called batching. Separate deliberate events, such as two clicks, are handled separately.

## Syntax and key APIs

```jsx
const [value, setValue] = useState(initial);
const [data, setData] = useState(() => expensiveInit());

setValue(next);          // replace
setValue(prev => next);  // compute from the latest queued value
```

Objects and arrays in state must be treated as immutable. React compares with `Object.is`, so a mutated object looks unchanged.

## Simple example

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount((c) => c + 1)}>
      Clicked {count} times
    </button>
  );
}
```

## Industry examples

### Update nested state immutably

```jsx
function rename(user, name) {
  return { ...user, profile: { ...user.profile, name } };
}

setUser((user) => rename(user, "Ada"));
setItems((items) => items.map((i) => (i.id === id ? { ...i, done: true } : i)));
setItems((items) => items.filter((i) => i.id !== id));
```

### Derive instead of duplicating

Storing a filtered list in state creates two sources of truth.

```jsx
function Products({ products }) {
  const [query, setQuery] = useState("");
  const visible = products.filter((p) => p.name.includes(query));

  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <p>{visible.length} results</p>
    </>
  );
}
```

### Model exclusive states

A single status value prevents impossible combinations like loading and error together.

```jsx
const [request, setRequest] = useState({ status: "idle" });
// { status: "loading" }
// { status: "success", data }
// { status: "error", error }
```

## Patterns and best practices

- Use an updater function when the new value depends on the old one.
- Keep the minimum state, and calculate everything else.
- Group values that change together.
- Store an ID for selection, not a copy of the object.

## Alternatives and trade-offs

| Need | Option | Trade-off |
| --- | --- | --- |
| Local, simple value | `useState` | Logic can scatter across handlers |
| Complex transitions | `useReducer` | More code |
| Value that doesn't affect output | `useRef` | No re-render |
| Server data | A data-fetching library or framework | Additional concepts |

## Common mistakes

**Reading state right after setting it.** The variable still holds this render's snapshot.

**Mutating state.** `items.push(x); setItems(items)` passes the same reference, so React can skip the update.

**Copying props into state.** The copy won't follow later prop changes.

**Expecting double logs to be a bug.** Strict Mode calls components twice in development to expose impurity.

## Interview questions

<Question q="Why doesn't setState update the variable immediately?">
The variable is a constant in the current render's snapshot. The setter queues a change for the next render.
</Question>

<Question q="What is batching?">
React processes all state updates from one event handler in a single render pass, including across components.
</Question>

<Question q="What is the difference between render and commit?">
Render calls components to compute the desired UI. Commit applies the differences to the DOM.
</Question>

## What it is

Reconciliation is how React compares a new render with the previous one to work out what changed. State belongs to a **position in the UI tree**, not to your JSX or the component function.

## Why it exists

Rebuilding the whole DOM on each update would be slow and would lose focus and scroll position. Matching old and new elements lets React reuse nodes and preserve state.

## How it works

React preserves a component's state as long as the same component type stays at the same position. A different type at that position resets its entire subtree. In a list, a `key` becomes part of the position, so an item keeps its state when it moves.

## Syntax and key APIs

```jsx
{items.map((item) => <Row key={item.id} item={item} />)}

<Profile key={userId} userId={userId} />
```

Keys only need to be unique among siblings.

## Simple example

Both branches render a `Counter` at the same position, so state is preserved between them.

```jsx
{isFancy ? <Counter color="gold" /> : <Counter color="gray" />}
```

Give them different keys and React treats them as different components:

```jsx
{isFancy ? <Counter key="fancy" color="gold" /> : <Counter key="plain" color="gray" />}
```

## Industry examples

### Reset a form when the record changes

Clearing many fields in an Effect is error-prone. A new key mounts a fresh instance.

```jsx
function EditPage({ customer }) {
  return <CustomerForm key={customer.id} customer={customer} />;
}
```

### Generate keys when data is created

```jsx
function addTodo(text) {
  setTodos((todos) => [...todos, { id: crypto.randomUUID(), text }]);
}
```

### Keep a stable type for inputs

Keeping one element at one position preserves focus during a layout change.

```jsx
function Field({ compact }) {
  return (
    <div className={compact ? "row" : "stack"}>
      <input />
    </div>
  );
}
```

## Patterns and best practices

- Use IDs that come from the data.
- Use an index only for static lists that never reorder.
- Use a key deliberately to reset state.
- Don't change an element's wrapper type conditionally, or you lose the state beneath it.

## Alternatives and trade-offs

| Goal | Option | Trade-off |
| --- | --- | --- |
| Keep state across removal | Lift it to a parent | More props |
| Hide without losing state | `Activity` or CSS | Stays in memory |
| Reset state | Change `key` | Remounts the subtree |

## Common mistakes

**Generating keys during render.** `key={Math.random()}` remounts every row each time and loses state.

**Using an index for a sortable list.** State attaches to positions, not items.

**Declaring a component inside another.** Its function identity changes each render, which is a different type, so its state resets.

**Expecting keys to be global.** They only specify position within the parent.

## Interview questions

<Question q="Why does React need keys?">
They tell React which item is which across renders so it can match, move, add or remove elements and keep the right state.
</Question>

<Question q="When does React reset a component's state?">
When it's removed from the tree, or when a different type or key appears at its position.
</Question>

<Question q="Is using the index as a key always wrong?">
No. It's acceptable when the list is static and items have no state. It's a bug source when items can reorder, insert or delete.
</Question>

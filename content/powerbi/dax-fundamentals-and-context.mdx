## What it is

DAX is the formula language of Power BI semantic models. A **measure** is computed at query time in the current filter context. A **calculated column** is computed row by row at refresh and stored.

## Why it exists

A model must answer unforeseen questions: one `Total Sales` definition has to work by month, product, region and any combination. DAX achieves that by computing based on context instead of cell positions.

## How it works

**Filter context** is the set of filters on the model when a measure is evaluated. It comes from rows and columns in a visual, slicers, page filters and `CALCULATE`.

**Row context** is "the current row", which exists inside calculated columns and iterators. A row context doesn't filter other tables on its own.

| | Measure | Calculated column |
| --- | --- | --- |
| Evaluated | When queried | At refresh |
| Context | Filter context | Row context |
| Storage | Formula only | Stored in the model |
| Good for | Aggregations and KPIs | Row-level attributes for slicing |

## Syntax and key APIs

```text
Total Units = SUM ( Sales[Units] )
Revenue = SUMX ( Sales, Sales[Units] * Sales[Price] )
Avg Price = DIVIDE ( [Revenue], [Total Units] )
Size Band = IF ( Sales[Units] >= 10, "Bulk", "Small" )   -- calculated column
```

`DIVIDE` handles division by zero safely. Reference measures as `[Measure]` and columns as `Table[Column]`.

## Simple example

Revenue on the sample table is 1,800 in total, and 650 for North. `Avg Price` at the total is 1800 ÷ 38 = 47.37. A column-averaged price would give a different and incorrect number, since it ignores units.

## Industry examples

Finance builds a base measure library, such as Revenue, COGS, and Margin %, and layers time-based analysis on top. Certified shared semantic models expose those definitions across the company.

## Patterns and best practices

- Prefer measures to calculated columns for aggregations.
- Build simple base measures, then reuse them.
- Format measures once, in the model.
- Store numbers as additive facts in the source when you can.

## Alternatives and trade-offs

Compute stable row-level attributes in Power Query or the warehouse, rather than as DAX columns. SQL views offer shared logic, but they cannot react dynamically to report filters.

## Common mistakes

- Using a calculated column for something that should react to slicers.
- Assuming totals are sums of displayed rows.
- Dividing with `/` where `DIVIDE` is safer.
- Implicit measures from dragging numeric fields around.

## Interview questions

<Question q="What is the difference between filter and row context?">Filter context restricts the data that a calculation sees. Row context identifies a current row during iteration, and doesn't propagate through relationships without context transition.</Question>

<Question q="Why doesn't a measure total equal the sum of its rows?">The total is calculated independently in its own filter context, which is correct for non-additive calculations such as ratios.</Question>

## What it is

**Context transition** is when `CALCULATE` converts the current row context into an equivalent filter context. Every measure reference is implicitly wrapped in `CALCULATE`.

## Why it exists

Row context doesn't filter a table or its relations by itself. Context transition lets a calculation "for this customer" work inside an iteration over customers.

Context transition isn't supported in DirectQuery calculated columns or RLS rules, and it can be expensive on large tables.

## Syntax and key APIs

```text
Column inside Customer:  Customer Revenue = [Revenue]
Without transition, a plain SUM would see all rows:
Wrong Column = SUM ( Sales[Amount] )

Rank = RANKX ( ALL ( DimCustomer[Name] ), [Revenue], , DESC, DENSE )

Big Customers =
SUMX (
    VALUES ( DimCustomer[CustomerKey] ),
    IF ( [Revenue] > 10000, [Revenue] )
)

New Customers =
VAR Period = VALUES ( DimDate[Date] )
RETURN
COUNTROWS (
    FILTER (
        VALUES ( Sales[CustomerKey] ),
        CALCULATE ( MIN ( Sales[Date] ), ALL ( DimDate ) ) IN Period
    )
)
```

## Simple example

Add a `Customer Revenue` column to `DimCustomer` using `= [Revenue]`. Each row gets its own customer's revenue. Replace it with `= SUM(Sales[Amount])` and each row shows the grand total, because no transition occurred.

## Industry examples

Dynamic ABC segmentation, cohort measures and Top-N analysis all rely on iterating a dimension with a measure.

## Patterns and best practices

- Iterate over a column with unique values.
- Reduce the iteration table first.
- Separate base measures from analytical patterns.
- Use DAX Studio to check query timings.

## Alternatives and trade-offs

Pre-computing customer attributes in the warehouse is simpler and faster when the logic doesn't depend on filters.

## Common mistakes

- Iterating over a table with duplicate rows.
- Using measures in row-heavy iterators without testing cost.
- Forgetting `ALL` in `RANKX`.
- Using calculated columns for dynamic logic.

## Interview questions

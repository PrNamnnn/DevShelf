## What it is

An end-to-end blueprint for a sales performance report covering requirements, model, measures, layout, security and rollout.

## Why it exists

Individual skills don't guarantee a trustworthy product. This shows how the decisions fit together.

## Syntax and key APIs

```text
Revenue = SUMX ( Sales, Sales[Units] * Sales[Unit Price] )
Revenue LY = CALCULATE ( [Revenue], SAMEPERIODLASTYEAR ( DimDate[Date] ) )
Revenue YoY % = DIVIDE ( [Revenue] - [Revenue LY], [Revenue LY] )
Target Attainment = DIVIDE ( [Revenue], [Target] )
```

## Simple example

Acceptance test: the report's FY total must match the general ledger to within an agreed tolerance, and a regional manager test account must see only their region.

## Industry examples

Common follow-up projects are finance P&L, HR attrition, supply chain service level and marketing funnel reporting, which use the same pattern with different facts.

## Patterns and best practices

- Write a data dictionary with the model.
- Reconcile before reviewing the visuals.
- Gather feedback on a prototype quickly.
- Track usage metrics after launch.

## Alternatives and trade-offs

A small team may not need a full pipeline. A monthly Excel pack may be enough when a report has few users.

## Common mistakes

- Starting with visuals.
- No named owner.
- No reconciliation to a trusted source.
- Skipping end-user testing.

## What it is

An aggregation pipeline passes documents through ordered stages, each one transforming the stream.

## Why it exists

It performs filtering, joining, reshaping and summarizing on the server, which is MongoDB's counterpart to `SELECT ... JOIN ... GROUP BY` and the core data-transformation tool in the database.

Stages that sort or group can run into a memory limit per stage, and `allowDiskUse` permits spilling to disk. The optimizer may reorder or merge stages, but it can't replace good pipeline design.

## Syntax and key APIs

| Stage | SQL analog |
| --- | --- |
| `$match` | `WHERE` or `HAVING` |
| `$project`, `$set` | `SELECT` expressions |
| `$group` | `GROUP BY` |
| `$sort`, `$limit` | `ORDER BY`, `LIMIT` |
| `$lookup` | `LEFT JOIN` |
| `$unwind` | Unnest an array |
| `$merge`, `$out` | Write results |

## Simple example

```js
import assert from "node:assert/strict";
import { MongoClient } from "mongodb";

const client = new MongoClient(process.env.MONGODB_URI);
const db = client.db("shelf_aggregation");
await db.dropDatabase();

await db.collection("products").insertMany([
  { _id: "A", category: "stationery" },
  { _id: "B", category: "books" },
]);
await db.collection("orders").insertMany([
  { status: "paid", items: [{ sku: "A", qty: 10, price: 20 }, { sku: "B", qty: 1, price: 150 }] },
  { status: "paid", items: [{ sku: "B", qty: 3, price: 150 }] },
  { status: "open", items: [{ sku: "A", qty: 99, price: 20 }] },
]);

const rows = await db.collection("orders").aggregate([
  { $match: { status: "paid" } },
  { $unwind: "$items" },
  { $lookup: { from: "products", localField: "items.sku", foreignField: "_id", as: "product" } },
  { $unwind: "$product" },
  { $group: { _id: "$product.category", revenue: { $sum: { $multiply: ["$items.qty", "$items.price"] } } } },
  { $sort: { revenue: -1 } },
]).toArray();

assert.deepEqual(rows, [{ _id: "books", revenue: 600 }, { _id: "stationery", revenue: 200 }]);

await db.dropDatabase();
await client.close();
```

## Industry examples

Analytics APIs build reports, and `$merge` maintains rollup collections on a schedule. ETL jobs reshape documents before loading to a warehouse.

## Patterns and best practices

- `$match` and `$sort` early, when an index can serve them.
- Use `$project` near the end, unless reducing fields helps a stage.
- Build pipelines stage by stage and test each one.
- Keep `$lookup` targets indexed.

## Alternatives and trade-offs

For heavy, wide analytics, a columnar warehouse is better. Atlas Stream Processing and change streams serve continuous pipelines.

## Common mistakes

- `$group` before `$match`.
- `$unwind` silently dropping documents with empty arrays.
- Repeated `$lookup` on a poor schema.
- Assuming pipeline order doesn't matter.

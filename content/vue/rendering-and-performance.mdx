## What it is

Vue renders through a Virtual DOM, but its compiler analyzes templates ahead of time, so the runtime compares only what can change.

## Why it exists

A pure Virtual DOM must walk the whole tree on each update because it can't know what's static. Templates are analyzable, so Vue moves that knowledge to build time.

## How it works

Rendering has three stages: **compile** templates to render functions, **mount** by running them inside a reactive effect, and **patch** when a dependency changes.

`v-if` and `v-for` create new block nodes, because they can change structure.

## Syntax and key APIs

| Tool | Effect |
| --- | --- |
| `v-once` | Render once, then treat as static |
| `v-memo="[a, b]"` | Skip a subtree unless listed values change |
| `shallowRef` | Avoid deep reactive proxies |
| `defineAsyncComponent` | Split a component's code |
| `<KeepAlive>` | Cache component instances |

## Simple example

```vue
<template>
  <header v-once>
    <h1>{{ appName }}</h1>
  </header>
</template>
```

## Industry examples

### Selection in a very large list

Only the rows whose selected state changes need to update. `v-memo` must be on the same element as `v-for`, and the docs describe this for lists over 1000 items.

```vue
<template>
  <div v-for="item in list" :key="item.id" v-memo="[item.id === selected]">
    {{ item.label }} {{ item.id === selected ? "selected" : "" }}
  </div>
</template>
```

### Lazy route and component loading

```javascript
const Chart = defineAsyncComponent(() => import("./Chart.vue"));
```

### Keep props stable

A child updates when any of its props changes, so passing a value that changes for every row updates every row.

```vue
<!-- Every row updates when activeId changes -->
<Row v-for="r in rows" :key="r.id" :id="r.id" :active-id="activeId" />

<!-- Only two rows change -->
<Row v-for="r in rows" :key="r.id" :id="r.id" :active="r.id === activeId" />
```

## Patterns and best practices

- Prefer templates, which get full compiler optimization.
- Virtualize long lists rather than rendering every row.
- Use `shallowRef` for big immutable data.
- Lazy-load routes.
- A build-step template compiler saves about 14 kB min+gzip of runtime.

## Alternatives and trade-offs

| Technique | Use when | Trade-off |
| --- | --- | --- |
| `v-show` | Frequent toggles | Initial render cost |
| `v-if` | Rare toggles | Mount cost on each change |
| `v-memo` | Proven hot lists | Stale output if a value is omitted |
| Virtual list | Very long lists | Library and measurement constraints |
| Render function | Highly dynamic structure | Fewer optimizations |

## Common mistakes

**Using `v-memo` inside `v-for`.** It doesn't work there. Put it on the same element.

**Omitting a dependency from `v-memo`.** The subtree won't update when it should.

**Deep reactive wrappers on huge API responses.** Deep proxies add a cost on each access.

**Blaming the framework first.** Profile with Vue DevTools and the browser's performance panel.

## Interview questions

<Question q="What are patch flags?">
Numbers the compiler adds to vnodes describing what can change, so the runtime checks only those aspects.
</Question>

<Question q="What is tree flattening?">
A block keeps a flat list of its dynamic descendants, so updates skip static structure.
</Question>

<Question q="When would you use v-memo?">
Rarely: mainly in very large `v-for` lists where a measurable update cost can be tied to a few values.
</Question>

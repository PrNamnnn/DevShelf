## What it is

Maintenance protects data and performance: backups for recovery, permissions for security, and routine checks for integrity.

## Why it exists

Hardware fails and mistakes happen. The real question is how much data you can lose and how quickly you can return.

## How it works

The **recovery model** determines how the log behaves.

| Model | Log backups | Point-in-time restore |
| --- | --- | --- |
| Simple | No | No |
| Full | Yes | Yes |
| Bulk-logged | Yes | Limited |

A **login** authenticates to the server. A **user** maps a login to a database. Permissions go to roles, and users join roles.

## Syntax and key APIs

```plsql
BACKUP DATABASE Sales TO DISK = 'D:\b\Sales.bak' WITH COMPRESSION, CHECKSUM;
BACKUP LOG Sales TO DISK = 'D:\b\Sales.trn' WITH CHECKSUM;
RESTORE VERIFYONLY FROM DISK = 'D:\b\Sales.bak';
RESTORE DATABASE Sales FROM DISK = 'D:\b\Sales.bak' WITH NORECOVERY;
RESTORE LOG Sales FROM DISK = 'D:\b\Sales.trn' WITH STOPAT = '2026-11-09T10:15', RECOVERY;
DBCC CHECKDB (Sales) WITH NO_INFOMSGS;
```

## Simple example

```sql
SELECT TOP (1) CASE WHEN recovery_model_desc IN ('SIMPLE','FULL','BULK_LOGGED') THEN 'ok' END
FROM sys.databases WHERE name = 'tempdb';
-- output: ok
```

## Industry examples

### Check recent backups

```sql
SELECT TOP (1) 'ok' FROM (SELECT 1 AS x) t
LEFT JOIN msdb.dbo.backupset b ON 1 = 0;
-- output: ok
```

```plsql
SELECT d.name, MAX(b.backup_finish_date) AS last_backup
FROM sys.databases d
LEFT JOIN msdb.dbo.backupset b ON b.database_name = d.name
GROUP BY d.name;
```

### Grant least privilege

```plsql
CREATE LOGIN app_login WITH PASSWORD = '...';
CREATE USER app_user FOR LOGIN app_login;
CREATE ROLE app_rw;
GRANT SELECT, INSERT, UPDATE ON SCHEMA::dbo TO app_rw;
ALTER ROLE app_rw ADD MEMBER app_user;
```

### Maintain statistics

Current statistics usually matter more than index rebuilds.

```plsql
UPDATE STATISTICS dbo.Orders WITH FULLSCAN;
ALTER INDEX ix_customer ON dbo.Orders REORGANIZE;
```

## Patterns and best practices

- Set backup frequency from the data loss you can accept.
- Regularly test restores, not only backups.
- Run `DBCC CHECKDB` on a schedule.
- Keep backups off the database server.
- Avoid granting `sysadmin` or `db_owner` to applications.

## Alternatives and trade-offs

| Need | Option | Trade-off |
| --- | --- | --- |
| Point-in-time restore | Full model | Log backups required |
| Simplicity | Simple model | Loses data since last backup |
| High availability | Always On groups | Infrastructure |

## Common mistakes

**Full recovery with no log backups.** The log grows until the disk fills.

**Shrinking databases routinely.** It fragments indexes, and the files just grow back.

**Assuming high availability replaces backups.** Mistakes replicate too.

**Rebuilding all indexes nightly.** It's often wasted work and log volume.

## Interview questions

<Question q="Login versus user?">
A login authenticates at the server level. A user is a database principal mapped to a login.
</Question>

<Question q="Why does the transaction log keep growing?">
Commonly the database uses the full recovery model without log backups, or a long-running transaction prevents truncation.
</Question>

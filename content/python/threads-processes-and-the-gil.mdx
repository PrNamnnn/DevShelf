## What it is

The **Global Interpreter Lock** lets only one thread execute Python bytecode at a time on standard CPython. Threads still help with waiting, and processes give real parallelism.

## Why it exists

The GIL protects CPython's internals, such as reference counts, and keeps single-threaded code fast and C extensions simple.

| Workload | Tool | Reason |
| --- | --- | --- |
| Many network waits | `asyncio` | Cheap tasks |
| Blocking I/O libraries | `ThreadPoolExecutor` | GIL released while waiting |
| CPU-bound Python | `ProcessPoolExecutor` | Separate interpreters |

The GIL doesn't make your code thread-safe. A compound operation like `count += 1` can still interleave.

## Syntax and key APIs

```py
from concurrent.futures import ThreadPoolExecutor, as_completed

with ThreadPoolExecutor(max_workers=8) as pool:
    futures = [pool.submit(fetch, url) for url in urls]
    for future in as_completed(futures):
        print(future.result())

results = list(pool.map(fetch, urls))
```

Only picklable objects can cross a process boundary. `sys._is_gil_enabled()` reports the GIL's status at runtime.

## Simple example

```python
from concurrent.futures import ThreadPoolExecutor
import time

def wait(n):
    time.sleep(0.05)
    return n * 2

start = time.perf_counter()
with ThreadPoolExecutor(max_workers=4) as pool:
    results = list(pool.map(wait, range(4)))
elapsed = time.perf_counter() - start

assert results == [0, 2, 4, 6]
assert elapsed < 0.15
```

## Industry examples

### Protect shared state

```python
import threading

class Counter:
    def __init__(self):
        self.value = 0
        self._lock = threading.Lock()

    def add(self):
        with self._lock:
            self.value += 1

counter = Counter()
threads = [threading.Thread(target=lambda: [counter.add() for _ in range(1000)]) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()

assert counter.value == 4000
```

### Handle failures per task

`result()` re-raises the worker's exception.

```python
from concurrent.futures import ThreadPoolExecutor, as_completed

def work(n):
    if n == 1:
        raise ValueError("bad")
    return n

with ThreadPoolExecutor() as pool:
    futures = {pool.submit(work, n): n for n in range(3)}
    ok, failed = [], []
    for future in as_completed(futures):
        try:
            ok.append(future.result())
        except ValueError:
            failed.append(futures[future])

assert sorted(ok) == [0, 2]
assert failed == [1]
```

### Pass work between threads

```python
import queue, threading

jobs = queue.Queue()
done = []

def worker():
    while (item := jobs.get()) is not None:
        done.append(item * 2)
        jobs.task_done()

thread = threading.Thread(target=worker)
thread.start()
for i in range(3):
    jobs.put(i)
jobs.put(None)
thread.join()

assert done == [0, 2, 4]
```

## Patterns and best practices

- Prefer `concurrent.futures` to raw threads.
- Share data with queues, not global variables.
- Check `sys._is_gil_enabled()` rather than assuming the build type.
- Use `max_workers` deliberately on shared systems.

## Alternatives and trade-offs

| Option | Benefit | Cost |
| --- | --- | --- |
| Threads | Shared memory, simple | Races, GIL for CPU work |
| Processes | Real parallelism | Pickling and memory overhead |
| asyncio | Huge numbers of waits | Needs async libraries |
| Free-threaded build | Parallel threads | About 1 to 8% single-thread cost, extension support varies |

## Common mistakes

**Using threads for CPU work and expecting speedup.** On a GIL build they take turns.

**Thinking the GIL prevents races.** Use locks for read-modify-write.

**Using a process pool in an interactive session.** `__main__` must be importable.

**Ignoring `future.result()`.** An exception stays hidden until you ask for it.

## Interview questions

<Question q="What is the GIL?">
A lock in standard CPython that allows one thread at a time to run Python bytecode.
</Question>

<Question q="Do threads help in Python?">
Yes, for I/O-bound work, because the GIL is released during blocking I/O. CPU-bound work needs processes or a free-threaded build.
</Question>

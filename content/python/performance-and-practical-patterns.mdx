## What it is

Performance work means finding the actual slow part and fixing it. Practical patterns are habits that keep code correct and readable as it grows.

## Why it exists

Intuition about speed is often wrong. A 100× gain usually comes from changing an algorithm or removing I/O, not from micro-tuning.

## How it works

Work through the layers in order, as the biggest wins come first.

## Syntax and key APIs

```bash
python -m timeit "sum(range(1000))"
python -m cProfile -s cumtime app.py
```

## Simple example

```python
import timeit

setup = "data = list(range(20000)); wanted = set(range(0, 20000, 100))"
as_list = timeit.timeit("[x for x in data[:2000] if x in lst]", setup + "; lst = list(wanted)", number=1)
as_set = timeit.timeit("[x for x in data[:2000] if x in wanted]", setup, number=1)

assert as_set < as_list
```

## Industry examples

### Profile in code

```python
import cProfile, io, pstats

def slow():
    return sum(i * i for i in range(10000))

profiler = cProfile.Profile()
profiler.runcall(slow)

out = io.StringIO()
pstats.Stats(profiler, stream=out).sort_stats("cumulative").print_stats(3)
assert "slow" in out.getvalue()
```

### Prefer early returns

```python
def discount(user):
    if user is None:
        return 0
    if not user.get("active"):
        return 0
    return 10 if user.get("vip") else 5

assert discount({"active": True, "vip": True}) == 10
assert discount(None) == 0
```

### Group with one pass, not nested loops

```python
orders = [{"user": 1, "t": 5}, {"user": 2, "t": 3}, {"user": 1, "t": 2}]

totals = {}
for order in orders:
    totals[order["user"]] = totals.get(order["user"], 0) + order["t"]

assert totals == {1: 7, 2: 3}
```

### Write a small test

```python
import unittest

def slugify(text):
    return "-".join(text.lower().split())

class SlugTests(unittest.TestCase):
    def test_spaces(self):
        self.assertEqual(slugify("A  B"), "a-b")

suite = unittest.defaultTestLoader.loadTestsFromTestCase(SlugTests)
result = unittest.TextTestRunner(verbosity=0, stream=open("nul" if __import__("os").name == "nt" else "/dev/null", "w")).run(suite)
assert result.wasSuccessful()
```

## Patterns and best practices

- Measure with realistic data.
- Pick the right data structure first.
- Use comprehensions and built-ins for simple transformations.
- Inject dependencies so you can test without real services.
- Keep functions small and side effects at the edges.

## Alternatives and trade-offs

| Technique | Gain | Cost |
| --- | --- | --- |
| Better algorithm | Often huge | Thinking time |
| `lru_cache` | Repeated calls | Memory, staleness |
| NumPy | Numeric loops | Dependency |
| Multiprocessing | CPU parallelism | Overhead |

## Common mistakes

**Optimizing without profiling.** You'll speed up the wrong code.

**String concatenation in a loop.** Use `join`.

**Query-per-row in a loop.** Batch it. This is usually the largest cost.

**Benchmarking tiny inputs.** Complexity differences appear only at scale.

## Interview questions

<Question q="How do you find a Python performance problem?">
Reproduce it with realistic data, profile with `cProfile` or a sampling profiler, and fix the dominant cost.
</Question>

<Question q="Why might list membership be slow?">
Each `in` scans the list. A set does a hash lookup, on average in constant time.
</Question>

## What it is

A transaction groups statements so that they succeed or fail as a unit. **MVCC** (multiversion concurrency control) keeps several row versions, so readers and writers don't block one another.

## Why it exists

Concurrent users would otherwise see half-finished work or overwrite each other. The docs summarize MVCC's benefit: reading never blocks writing, and writing never blocks reading.

## How it works

An `UPDATE` writes a new row version and marks the old one as expired. Each statement or transaction sees versions according to its snapshot.

| Level | Snapshot | Notes |
| --- | --- | --- |
| Read Uncommitted | Per statement | Behaves like Read Committed in PostgreSQL |
| Read Committed (default) | Per statement | Non-repeatable reads are possible |
| Repeatable Read | Per transaction | Phantom reads don't occur in PostgreSQL |
| Serializable | Per transaction, with SSI | As if run one at a time |

## Syntax and key APIs

```plsql
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT ...;
COMMIT;

SELECT * FROM jobs WHERE id = 1 FOR UPDATE;
SELECT * FROM jobs FOR UPDATE NOWAIT;
SELECT * FROM jobs FOR UPDATE SKIP LOCKED;
```

## Simple example

```sql
CREATE TABLE accounts (id int PRIMARY KEY, balance int CHECK (balance >= 0));
INSERT INTO accounts VALUES (1, 100), (2, 0);

BEGIN;
UPDATE accounts SET balance = balance - 40 WHERE id = 1;
UPDATE accounts SET balance = balance + 40 WHERE id = 2;
COMMIT;

SELECT balance FROM accounts ORDER BY id;
-- rows: [{"balance":60},{"balance":40}]
```

## Industry examples

### Partial rollback with savepoints

```sql
BEGIN;
UPDATE accounts SET balance = 1 WHERE id = 1;
SAVEPOINT step;
UPDATE accounts SET balance = 2 WHERE id = 1;
ROLLBACK TO step;
COMMIT;

SELECT balance FROM accounts WHERE id = 1;
-- rows: [{"balance":1}]
```

### Watch new row versions appear

`xmin` is the ID of the transaction that created a row version.

```sql
CREATE TABLE versions (id int);
INSERT INTO versions VALUES (1);
CREATE TEMP TABLE before AS SELECT xmin::text AS x FROM versions;
```

Run the update as its own transaction, then compare.

```sql
UPDATE versions SET id = 2;
```

```sql
SELECT (SELECT x FROM before) <> (SELECT xmin::text FROM versions) AS changed;
-- rows: [{"changed":true}]
```

### A safe job queue

`SKIP LOCKED` lets multiple workers each claim different rows. The docs note it gives an inconsistent view, so use it for queue-like tables only.

```plsql
UPDATE jobs SET status = 'running'
WHERE id = (
  SELECT id FROM jobs
  WHERE status = 'pending'
  ORDER BY id
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
RETURNING *;
```

### Retry serialization failures

At Repeatable Read and Serializable, conflicting transactions fail with SQLSTATE `40001`. Retry the **whole** transaction.

```py
for attempt in range(5):
    try:
        with conn.transaction():
            run_business_logic(conn)
        break
    except SerializationFailure:
        time.sleep(0.05 * 2 ** attempt)
```

## Patterns and best practices

- Keep transactions short, and never wait on users or networks inside one.
- Acquire locks in a consistent order to prevent deadlocks.
- Handle `40001` and deadlock errors with retries.
- Use `READ ONLY` for read-only serializable transactions.

## Alternatives and trade-offs

| Technique | Protects against | Cost |
| --- | --- | --- |
| Atomic `UPDATE x = x + 1` | Lost updates | Simple cases only |
| `SELECT FOR UPDATE` | Conflicting writers | Blocks others |
| Version column | Lost updates | App retry logic |
| Serializable | All anomalies | Retries required |

## Common mistakes

**Assuming a sequence rolls back.** Sequence changes aren't undone.

**Leaving transactions idle.** They hold locks and prevent vacuum from removing old rows.

**Using read-then-write at Read Committed.** Two sessions can both read and then write, losing an update.

**Retrying only the failed statement.** The transaction's whole logic must rerun.

## Interview questions

<Question q="How do readers avoid blocking writers?">
MVCC keeps old row versions, so a reader sees a consistent snapshot while a writer creates a new version.
</Question>

<Question q="What is the default isolation level?">
Read Committed. Each statement sees data committed before it began.
</Question>

<Question q="How does PostgreSQL handle a deadlock?">
It detects it automatically and aborts one transaction. Which one is unpredictable, so applications should retry.
</Question>

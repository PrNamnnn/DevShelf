## What it is

A **B-tree** lets the database find a key in a few page reads. The planner picks one of three **join algorithms** by comparing estimated costs.

## Why it exists

No join strategy is best for every input. Understanding them explains why a plan changes as data grows.

| Algorithm | Works by | Best when |
| --- | --- | --- |
| Nested Loop | For each outer row, search inner | Few outer rows, indexed inner |
| Hash Join | Build a hash table, then probe | Large, unsorted, equality joins |
| Merge Join | Walk two sorted inputs | Inputs already sorted |

## Syntax and key APIs

```sql
CREATE TABLE a (id int PRIMARY KEY, v int);
CREATE TABLE b (id int PRIMARY KEY, a_id int);
INSERT INTO a SELECT g, g FROM generate_series(1, 20000) g;
INSERT INTO b SELECT g, 1 + g % 20000 FROM generate_series(1, 20000) g;
CREATE INDEX b_a_id ON b (a_id);
ANALYZE a; ANALYZE b;
```

## Simple example

Fetching one row, the plan chooses a nested loop.

```sql
DO $$
DECLARE line text; plan text := '';
BEGIN
  FOR line IN EXPLAIN SELECT * FROM a JOIN b ON b.a_id = a.id WHERE a.id = 5 LOOP
    plan := plan || line;
  END LOOP;
  ASSERT plan LIKE '%Nested Loop%', plan;
END $$;
```

## Industry examples

### Scale changes the plan

Joining everything, the planner switches strategy.

```sql
DO $$
DECLARE line text; plan text := '';
BEGIN
  FOR line IN EXPLAIN SELECT count(*) FROM a JOIN b ON b.a_id = a.id LOOP
    plan := plan || line;
  END LOOP;
  ASSERT plan LIKE '%Hash Join%' OR plan LIKE '%Merge Join%', plan;
END $$;
```

### Sorted inputs enable merge

```sql
SET enable_hashjoin = off;
SET enable_nestloop = off;

DO $$
DECLARE line text; plan text := '';
BEGIN
  FOR line IN EXPLAIN SELECT * FROM a JOIN b ON b.a_id = a.id LOOP
    plan := plan || line;
  END LOOP;
  ASSERT plan LIKE '%Merge Join%', plan;
END $$;

RESET enable_hashjoin;
RESET enable_nestloop;
```

## Patterns and best practices

- Index foreign keys used in nested loops.
- Keep statistics fresh, because join choice depends on row estimates.
- Raise `work_mem` carefully for large sorts and hashes.
- Use `enable_*` settings for diagnosis, not as a production fix.

## Alternatives and trade-offs

| Situation | Likely choice | Watch for |
| --- | --- | --- |
| Few rows | Nested Loop | Bad if outer rows are underestimated |
| Reports | Hash Join | Memory, batches to disk |
| Both sorted | Merge Join | Sort cost if not already sorted |

## Common mistakes

**A nested loop with huge `loops`.** The outer estimate is usually wrong.

**Assuming indexes always help joins.** A hash join can ignore them.

**Disabling a planner method in production.** It hides the real problem.

**Too little `work_mem`.** Hashes and sorts spill to disk.

## Interview questions

<Question q="Why are B-trees shallow?">
Each page holds many keys, so fan-out is high and even huge tables need only a few levels.
</Question>

<Question q="When is a hash join a poor choice?">
For small outer inputs with an indexed inner table, or when memory is tight and it spills to disk.
</Question>

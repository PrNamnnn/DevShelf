## What it is

Data quality measures fitness for purpose. **Data leakage** occurs when a model or analysis uses information unavailable at the moment of prediction. A **reproducible pipeline** yields the same output from the same inputs and code.

## Why it exists

Decisions inherit the errors of their data. Leakage produces models that look excellent in testing and fail in production.

## How it works

| Dimension | Question | Example check |
| --- | --- | --- |
| Accuracy | Does it match reality? | Reconcile with finance |
| Completeness | Is anything missing? | Null rate, row counts |
| Consistency | Does it agree across systems? | Revenue in CRM vs warehouse |
| Timeliness | Is it fresh? | Latest load time |
| Validity | Does it meet its rules? | Range, enum, format |
| Uniqueness | Are keys unique? | Duplicate key count |
| Integrity | Do references resolve? | Orphaned foreign keys |

Types of leakage:

- **Target leakage:** a feature created after the outcome, like `refund_issued` when predicting a refund.
- **Train-test contamination:** preprocessing fitted on all data.
- **Temporal leakage:** future values in features.
- **Group leakage:** one customer appearing in both training and test.

## Worked example

A churn model scores an AUC of 0.99. Its most important feature is `days_since_last_login`, measured at data-extract time, after cancellation stopped logins. Rebuilding every feature "as of" a date before the prediction window brings AUC to 0.78. It's a less exciting number and a true one.

## Python

```python
import numpy as np
from sklearn.feature_selection import SelectKBest, f_classif
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import cross_val_score
from sklearn.pipeline import make_pipeline

rng = np.random.default_rng(0)
X = rng.normal(size=(100, 2_000))
y = rng.integers(0, 2, 100)

# Wrong: features chosen with knowledge of every label.
leaked_X = SelectKBest(f_classif, k=20).fit_transform(X, y)
leaked = cross_val_score(LogisticRegression(), leaked_X, y, cv=5).mean()

# Right: selection is refit inside each training fold.
pipe = make_pipeline(SelectKBest(f_classif, k=20), LogisticRegression())
honest = cross_val_score(pipe, X, y, cv=5).mean()

assert leaked > 0.75
assert 0.3 < honest < 0.7
```

The labels here are random, so honest accuracy is about 50%. Leakage alone creates the apparent skill.

## SQL

```sql
SELECT count(*) AS orphan_orders
FROM (VALUES (1, 10), (2, 11), (3, 99)) AS o(order_id, customer_id)
LEFT JOIN (VALUES (10), (11)) AS c(customer_id) USING (customer_id)
WHERE c.customer_id IS NULL;
-- rows: [{"orphan_orders":1}]
```

## In industry

Teams track quality as service-level objectives, with alerts and named owners. Point-in-time correct joins are the main way of avoiding temporal leakage.

## Assumptions and limitations

Quality is contextual. Data fit for trend reporting may be unfit for invoicing. Scores across dimensions don't combine into one meaningful number.

## Common mistakes

- Scaling or selecting features before splitting.
- Using a snapshot taken after the outcome.
- Random splitting customers with many rows.
- Treating a dashboard refresh as evidence of correct data.

## Alternatives

Feature stores with point-in-time joins enforce correctness at scale. Holding out the most recent period gives a realistic final check.
